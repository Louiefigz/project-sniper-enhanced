Licence, updates, backup and uninstall

The commercial terms, what version you have, and how to remove Sniper without losing your videos.

Updates — read this one carefully

Your purchase is the version you downloaded. It does not include bug fixes, compatibility updates or new versions.

Because that is the policy, here is the honest risk, stated rather than hidden:

RiskHow exposed you are
Your own Codex or Claude CLI auto-updatesHandled. This package installs its own pinned copies of both CLIs inside runtime/ and disables their auto-updater. An update to your global CLI does not affect Sniper.
A Python or Node package changes underneath youHandled. Both dependency sets and every Python package are pinned to exact versions, so a reinstall gets the same set this release was tested with.
Your provider retires the model, or changes what its sign-in check reports Not handled, and not fixable by you. Sniper checks the sign-in response strictly. If your provider changes it, this version stops being able to sign in, and a fix would be a new release you do not have rights to under this policy.
A major macOS upgrade breaks a dependencyNot handled. Same reason.

Which version you have

cat RELEASE.json

It records the version, the exact source it was built from, the platform it is qualified for, every component version, and — plainly — whether this build is sellable and what is blocking it. Quote the version field whenever you report a problem.

The archive's own checksum is deliberately not inside the archive. It is published beside the download in SHA256SUMS, because a hash stored inside a file cannot verify that file.

Going back to an earlier version

There is no in-place rollback, and that is on purpose. Each release is a separate folder with its own runtime/:

  1. Keep the old release folder. Do not delete it when you unzip a new one.
  2. Install the new one beside it and use it. If you created runtime/sniper.local.env in the old folder, copy it into the new one first.
  3. If the new one misbehaves, run install/stop.command in it and install/start.command in the old one.

Both point at the same ~/ProjectSniper, so your videos and your list of recent projects are shared between them. An export that was interrupted resumes only in the release folder that started it; in the other one, export again. A project created by a newer release may use plan fields an older one does not understand — if you plan to go back, copy the project folder first.

Backup

Back up ~/ProjectSniper. That is all of your work: your footage, your transcripts, your edit plans, your finished videos, your approval receipts and Sniper's list of recent projects. The Sniper folder itself is replaceable — you can always unzip it again.

Keeping your videos somewhere else

Put this one line in runtime/sniper.local.env (create the file if it does not exist), then stop and start Sniper:

SNIPER_WORKSPACE_ROOT=/Volumes/Work/SniperVideos

Back up that folder instead of ~/ProjectSniper.

Moving the Sniper folder

If you move or copy the Sniper folder after installing, its scripts refuse to start until you run install/install.command once in the new place. It redoes only the steps that record the folder's location, and keeps your settings.

Uninstall

install/uninstall.command

It asks you to type REMOVE, signs out the Codex or Claude login you made for Sniper (including the Claude login's Keychain item), then deletes what the installer created — runtime/ (including your own runtime/sniper.local.env settings; copy that file first if you want to keep it), the two node_modules folders, the Python environment, the app build, the render caches and the export-recovery history. Then delete the folder.

It does not touch your videos in ~/ProjectSniper, your own Node, Python, Homebrew, ffmpeg or whisper install, or your global Codex and Claude CLIs and their logins.
