# A two-hour first master for Project Sniper

Date: 2026-09-06. Status: implementation in progress following explicit operator authorization, with three independent adversarial agents and actual HyperFrames UI testing. The complete workflow and timing/quality promises remain unqualified. See [the implementation and measured-test log](TWO_HOUR_IMPLEMENTATION_LOG_2026-09-06.md) for current landed slices, failures and remaining work; the baseline findings below describe the original audit, not a fresh assertion that every defect is still present.

This plan answers the operator's current goal: cut first, let the user explain the treatment they want, and generate a quality 10-minute video in about two hours, with subsequent creative revision time reported separately. It is based on the current working tree, actual UI inspection, the local HyperFrames catalog and templates, retained execution evidence, and `video-editor-client 2.zip`. Existing application changes were inspected, not implemented by this review. The ZIP's instructional documents were treated as reference data.

The proposed product is one editor with a durable cut approval, a structured treatment brief, reusable visual recipes, independent audio/color/graphics preparation, and a bounded review-and-repair controller. Offer both guided cut-first and one-request autopilot approval policies on that same engine. Internal staging does not require repeated user interruptions. The largest opportunity is reducing repeated planning and review. Rendering also needs improvement, but the evidence does not identify encoding alone as the reason an edit takes hours.

This is an implementation sequence for the existing command-driven-editing work, not a replacement architecture. It narrows the first performance claim to a useful MP4 delivery workflow and explicitly includes audio and color quality. Existing P1–P5 mechanisms should be integrated where their exact operation is proved. Proposed changes below do not retroactively change existing job authority, review policy, or release claims.

## 2. Define the promise and its clocks

The first target is a **complete first master ready for user creative review**, with the requested lanes present, technical QC passed, scoped craft review complete, and exact output/proof bindings. It is not merely a storyboard or a low-resolution preview. The user's subsequent taste changes create a new revision.

Initial qualification workload, provisionally named `LF10-PRODUCED`:

- 10 minutes of 1080p output, one qualified frame rate/canvas/destination per run.
- Up to 30 aggregate minutes of raw footage, up to two camera/screen sources, local SSD; input up to 4K where the source path is qualified.
- Roughly 60–120 cut segments, up to 30 graphic occurrences and at most 30 distinct compiled graphics render keys, up to ten approved local b-roll assets, one dialogue program plus optional bed/SFX. Report graph units separately: they are not interchangeable with legacy render entries. Unique text or duration normally means a fresh render key.
- Known supported color transforms; representative camera/lighting groups included in the measured corpus.
- Registered/parametric recipes only for the first qualified class. Current custom scene authoring is a direct CLI mechanism, and its end-to-end GUI integration is additional work. Custom scenes are a separately estimated add-on until their authoring, command/UI routing, resource limits and final delivery qualify.
- Ordinary content-led longform density; no requirement to fill every second with graphics. A denser 60-graphic workload is a separately reported stress class, not silently excluded after it is slow.
- Already approved local assets/reference pack at start. External sourcing, novel style research, tracking/rotoscoping/3D and additional destinations have visible separate estimates before launch.

Count limits alone are insufficient. Admission must use the actual compiled workload: total rendered frames across unique keys, each template's raster area, alpha/opaque codec, simultaneous layers, retained intermediate bytes, decoded asset sizes and measured per-family cost. Prototype a 30-key/180 aggregate graphics-seconds/at-most-two-simultaneous-graphics profile at 1080p-equivalent raster and one frozen rate, then replace those provisional limits with pilot-calibrated ceilings before admitting jobs. Area means the rendered composition raster, not its small visible alpha box. Include full-frame long holds when the renderer must capture them. Also bound kept-word count, caption cue/shard count and total caption frames, b-roll decoded pixels, source/lighting/audio groups, required review evidence and queued jobs on the host. SRT sidecars and full-video karaoke are different workload classes. Source/codec decode limits and local free space are part of admission. A job outside these limits is estimated explicitly and remains in eligibility/fallback reporting. Recheck admission after the exact plan compiles, before expensive rendering; if it exceeds the estimate, retain time already spent and surface the changed scope/estimate.

The current review host is an Apple M3 Max with 64 GiB RAM and 16 logical CPUs (read from the system during this audit). Use it as the first declared target host, with its actual disk, power/thermal state and runtime pinned during measurement. Historical benchmark machine equivalence was not established by this review.

Declare the quality policy before admission: `LF10-AUTO` requires a connected, validated audio/temporal review capability for that source/risk class; `LF10-ASSISTED` includes a named operator audition checkpoint. The latter reports system time plus operator wait and cannot count as an automatically approved two-hour success. Both produce useful outputs; their readiness labels and acceptance criteria are different. The automatic class is not released until that reviewer capability and quality coverage exist.

Quality capability and creative approval policy are separate axes. `approvalPolicy: guided | autopilot` determines whether the user or authorized independent system reviewers approve the cut/treatment. It does not waive audiovisual review requirements. A guided project can have fully automatic technical review; an autopilot request may still need a disclosed operator audition when its source class is not automatically qualified. Do not label that latter result unattended completion.

Every run displays these clocks:

1. **Preparation/cut:** request acceptance through a reviewable cut, including probe, transcription, source diagnosis and system cut reviews.
2. **Generation:** acceptance of the user's first post-cut treatment brief through the full first master. For autopilot with an up-front brief, this phase starts immediately when the reviewed cut becomes available; no second user message is needed. Target at most 120 minutes, including storyboard/animation/sound/color proposal work, all queueing, retries, cache misses, internal repairs, and system-caused clarification. User or system confirmation of that proposal does not restart the clock. Any speculative treatment work before cut approval is also visible in total request time, not counted as a free speedup.
3. **Waiting for user:** recorded explicitly; it does not hide active system work. Show total wall time alongside active time.
4. **Later revisions:** measured from acceptance of each new edit through its scoped preview and approved master.

Never start the generation clock only after expensive treatment preparation is finished. Source facts legitimately computed during cut preparation may be reused, and their time remains visible on the preparation clock. Target preparation/cut active time of at most 35 minutes for the declared 30-minute-source class, to be tested independently; the corresponding overall system target is therefore at most 155 minutes plus genuine operator wait. Measure request-to-first-master as well so the cut step cannot become a new all-day bottleneck. A newly discovered system ambiguity stays on its original active clock; only an actual requested human decision can enter waiting state.

The initial class assumes local assets. For uploaded/remote footage, show transfer time in overall elapsed time separately from the local-media qualification; do not hide it behind a late request-acceptance timestamp or claim the local target covers unmeasured network transfer.

The initial two-hour goal is a qualification target, not a current guarantee or p95 claim. If an admitted job fails or overruns, count it. If a request is outside the supported class, show the reason and estimate before starting. A deadline cannot approve a failed video or silently remove a requested effect.

## 3. The user workflow to implement

The existing product contract already specifies two approval policies on one engine: [product and workflows](command-driven-editing/01_PRODUCT_AND_WORKFLOWS.md). Its full target remains proposed, although current compatibility Auto Edit already advances from system cut approval to visual authoring without a human stop. This plan must preserve that direction. One-shot means one user request can produce a complete first edit; it does not mean one indivisible model call, one render attempt, or zero internal validation.

**Guided mode — “Review my cut first.”** Use the explicit handoffs below when the user wants creative control before finishing:

```text
Choose footage and story goal
  → Prepare media and draft the cut
  → Review cut in video + transcript, correct words/retakes, approve exact cut
  → Submit treatment brief (generation clock starts), inspect visual/sound proposal
  → Confirm treatment brief and generation estimate
  → Generate parallel lanes, assemble, check, repair within budget
  → Watch the complete first master
  → Request a scoped change; see what will rebuild and its estimate
```

**Autopilot mode — “Handle the whole first edit.”** Accept story and treatment instructions together, including style examples, density, sound/color preferences and must-keep/must-avoid clauses. Persist each clause and its stage disposition; deferred treatment clauses must survive cut approval. Run the same cut, proposal, generation, review and repair stages internally, with independent system approvals bound to exact artifacts. Continue through preauthorized creative choices without asking the user to approve every storyboard or sample. Surface those intermediate artifacts for optional inspection. Pause only for a necessary unresolved user decision, unavailable required review capability, or an unrepairable blocking issue; conflicting instructions, missing licensed assets and unknown source transforms are not permission to guess silently. Failed gates cannot be bypassed to meet the deadline. Offer “stop after cut” and a user interrupt/override on the same job state.

Version the accepted autopilot profile and bind it to approval receipts: supported source class, canvas, style/recipes, rhythm/density, caption/music/color policy, approved assets, editorial discretion, must-keep rules and cost bounds. Approval depends on observable eligibility, resolved clauses and passing required evidence, not an invented numerical AI-confidence threshold. Changes to that profile invalidate the approvals they actually affect.

**Cut screen.** In guided mode the primary action is `Approve cut and continue`. Present removed ranges and uncertain edit points, not all pipeline internals. Audition before/after cut handles; preserve stable word/source IDs. A cut approval is a durable artifact bound to the cut revision, transcript and source identity and records whether the user or authorized system approved it. Existing independent cut reviews remain required in both modes. Stopping after the cut is a normal completed stage when requested.

This requires an authority change, not merely another screen: `cut-review-approval.ts:70` currently includes scope, the whole operator-intent digest and reference digest, while `auto-edit-authority-snapshot.ts:187` hashes the full stored/requested intent. Add versioned cut intent (story, duration, selected source/words, ordering and cut rules) and treatment intent (graphics, captions, music, look, layout). Classify reference changes by their actual cut/treatment dependencies. Treatment-only changes preserve the reviewed cut; story/duration/source/timing changes require cut review. Migrate existing approvals only through explicit verified reconstruction or re-review; never reinterpret old receipts as a narrower contract silently.

**Treatment brief.** Capture audience/goal, pacing, graphic density, examples or style, must-keep/must-avoid choices, captions, b-roll, music, cleanup and color look. Free text compiles to structured choices with a disposition for each requested clause. Make available 6–8 storyboard frames across the full video, one representative animated scene, and 10–20s source/processed audio and color A/B. An early preview uses the actual selected footage and user copy; stock template thumbnails are insufficient. This proposal has a ten-minute allocation inside the 120-minute generation clock. In guided mode, user confirmation authorizes the remaining treatment; the system can continue only independent reusable work during actual user wait, and that active work still counts. In autopilot, system reviewers confirm alignment with the accepted brief and authorized style policy, with no routine human stop. Later user changes to the brief get a new explicitly scoped revision clock rather than erasing time already spent.

**Progress.** Keep the preview/transcript usable while jobs run. Show the current work, completed lanes, elapsed time, expected range and latest reviewable artifact. Distinguish `needs your decision`, `system repair`, and `ready to review`. Derive estimates from measured host/job features; remove fixed claims such as audio rebuild being “about 3 minutes” (`editor/audio-panel.tsx:20`).

**Review and change.** Default to the finished output, a short list of material findings and optional comparison to the prior version. A copy edit shows the affected scene; music gain shows an audio preview; a global grade shows source-group A/B. Warn before a ripple cut changes later timings. Keep the last approved master available until the successor passes.

**MP4 / Palmier.** Let new jobs explicitly choose MP4 delivery or the Palmier workflow. Implement the two-hour claim for the MP4 route first; measure Palmier separately. Do not silently reinterpret an existing human-owned Palmier project. Such a project keeps its workflow or creates an explicit Sniper branch from a known approved source/cut.

**Observed UI fixes.** Browser inspection at 1600×1100 loaded an existing project and the Elements panel with write requests blocked. Opening Elements expanded the document to 16,361px; `editor-view-sections.tsx:255` uses `min-h-screen` without a bounded workspace height. Subsequent gallery passes surfaced four `gsap is not defined` errors after preview initialization. Browser diagnostics show GET requests for `/vendor/gsap/gsap.min.js`, `SplitText.min.js` and `/motion-tokens.js` blocked by ORB, plus icon responses blocked by the same-origin policy. These resource failures are distinct from deliberately blocked audit POSTs. Fix sandbox-compatible asset delivery and initialization rather than removing the preview sandbox. Constrain editor panes to viewport height with internal scrolling; retain transcript/player/timeline visibility, and test every eligible preview for runtime/asset failures. Recent-project action labels also overlap in the 1440px capture. Use one primary next action plus a compact secondary menu. The old project lacked a current approved preview, so this inspection is not a visual quality verdict on a newly rendered video.

## 4. Use the catalog to save authoring time

Extend `graphics/style_profiles.py`, `form_allocation.py`, the composition capability matrix and `src/lib/producer/comps-catalog.ts` together. Avoid another competing template registry.

Authority is explicit: composition HTML declarations and the existing source-derived `template_contract.py` own supported content fields; style profiles own editorial selection policy; per-composition measured capability owns tested constraints/eligibility. Generate UI schema/projections from those sources, adding only versioned field labels/widgets where needed. The UI must not become a separately writable truth about renderer support.

Each eligible recipe needs one shared schema covering:

- Information role: statement, comparison, evidence/chart, steps, chapter, screen focus, quote or annotation.
- Supported canvas/FPS, input types, text/row limits, minimum readable duration, assets, safe regions and presenter constraints.
- Cost features: animated seconds, raster area, transparency, media size, complexity class and measured render distribution on each qualified host.
- Animation event map, expected visibility phases and permissible overlap with captions/other graphics.
- Status: qualified for this route/profile, limited, experimental, or blocked; reasons are shown consistently to UI, planner and renderer.

Start with a complete, coherent set of roughly 12–15 existing recipe families across short and long use. First publish a role × aspect × delivery-profile matrix with exact existing kind bindings and gaps: chart-story and UI focus are wide; count-up and line-swap are vertical. Family count is not an exit criterion, and a missing role needs a separately estimated adaptation or an explicit limitation. Reuse a visual family through a video with varied information forms. Current fixed density windows and maximum-two-renderer-use rules belong to their original studied profile; do not apply them universally to ten-minute programs. Preserve explicit brand/style requirements and prevent monotonous adjacent reuse with chapter-aware rules and actual comprehension review.

Selection should produce structured content and timing, not write HTML on ordinary jobs. Let a model make narrative and information-shape decisions; code selects eligible renderers, validates payloads, fits text, resolves asset references and lays out safe regions. One recipe family may produce many fresh renders: new text/duration changes often invalidate rendered media. Prequalification saves reasoning and debugging; it does not mean all rendered frames are reusable.

Improve the Elements UI with search and filters for role, canvas, overlay/full-frame, complexity and qualification; a compact grid with one active preview; typed string/enum/list/chart/image controls; and clear missing-asset states. Existing properties mostly expose one primary text field plus numbers/colors, so many chart, line-swap and screenshot fields still need AI/JSON. Use schema-generated controls. `canvas-pip-list` is excluded by the allocator for gate failures but is still offered in the UI; qualification status must govern insertion.

Keep catalog expansion outside individual edit jobs. New imports get long-text, tiny-text, negative/large numbers, missing-asset, source-background, reverse-seek, FPS/aspect and real-footage tests before they become eligible. Qualify each composition's dependency closure; changing one HTML file should not require re-proving every unrelated composition. Shared fonts/tokens/runtime correctly invalidate affected dependents.

## 5. Reduce the expensive reasoning and repair loop

**Compile runtime doctrine.** Preserve the full captured corpus for provenance, but give each call a versioned packet containing the applicable rules, exact plan/brief, relevant transcript evidence, selected recipe schemas and current failure facts. Historical plans, unrelated style studies and the full failure ledger should not be re-read by every critic. Start with a measurable packet-size budget (for example 16–32KB of doctrine excluding necessary transcript/evidence), then tune it against defect recall and editorial quality. Size is a target, not permission to omit a required rule.

**Separate responsibilities.** Keep two independent plan reviews where required, with explicit lenses and the same immutable candidate. Reuse their machine evidence packet; keep reasoning independent. Deterministic work includes identifiers, timing, source availability, declared copy/values, frame counts, bounds and schema constraints. Craft work includes information choice, story structure, readability, cadence and whether a visual helps. Already-parallel reviews should not be parallelized again.

**Route failures before expensive work.** A failed deterministic check with a known fix creates a typed operation and relevant rechecks. A known unsupported renderer goes back to eligible selection. An ambiguous aesthetic concern goes to the appropriate lens with its evidence. Do not run both full visual critics on an already-doomed missing-asset or alpha-duration failure. Multiple defects should be grouped by common cause and fixed in one bounded batch.

**Do not reset everything for a local edit.** Extend current render-graph/revision mechanisms so proofs depend on their actual inputs. A title-copy change invalidates its asset/geometry, overlap windows, semantics and affected final pixels; it does not invalidate unchanged dialogue PCM. A music or global grade edit has broader program-level effects. A cut ripple invalidates downstream timing, captions and scenes. Every new final still gets format/duration/decode and global output checks. If dependency analysis cannot prove the smaller closure, take the full path and report the fallback.

Maintain compact global projections for claims/numbers, chapter/beat sequence, repeated hook content, visual rhythm/density, palette/source groups and terminology. A local edit that changes one projection invalidates its global editorial check even when other pixels are unchanged. Recheck that compact projection plus local temporal evidence; use full audiovisual review when the impact is broader or unknown. Seed contradictions/duplication spanning two scenes. Typed template substitution must preserve every requested information/visual obligation; it cannot silently replace an unsupported chart with unrelated decoration.

**Budget the whole request.** Store remaining work/retry budgets durably across restarts. Current per-invocation limits can reset on resume. One shared 30-minute repair reserve covers deterministic preflight failures, failed plan reviews, asset repairs and post-render QC; a new stage or resume never creates a fresh pool. Initial tasks and retries both consume the 120-minute active deadline. Detect repeated issue signatures and no-progress repairs. Admit a repair only if its predicted completion leaves enough reserved time for required final checks; otherwise preserve the best reviewable candidate and exact unresolved issue, recording a failed/overrun run. There may be no renderable candidate after an authoring failure: report that state honestly. Never delete the last approved output.

Do not make model downgrades the primary intervention. First reduce context, repeated decisions and preventable defects. Then compare model/effort tuples on frozen packets, seeded defects and blinded output quality for both configured providers. Current provider pins stay unchanged until that evidence supports a change.

## 6. Rendering and evidence architecture

Use the current pipeline and graph primitives; connect the supported paths end to end.

1. Source analysis runs once per content/runtime identity: probe, transcript, speech activity, audio features, shot/lighting groups, proxy/filmstrip and framing evidence. Store compact reusable analysis, not a new source of edit authority.
2. After cut/brief approval, execute independent audio, source-group color, caption and graphics preparation through one resource-aware scheduler. Workers have memory/CPU/IO budgets. Benchmark one, two and four graphics tasks before changing defaults; do not multiply outer task concurrency by unrestricted inner Chrome workers.
3. Legacy graphics currently launch a fresh single-worker CLI per item. First benchmark bounded process concurrency retaining per-comp isolation. Persistent browser pooling/batching is a later experiment requiring proof against DOM/font/timeline leakage, seek behavior and failure containment. The project-scene path already supports bounded concurrency; reuse its good mechanisms and charge proof decoders/compositors to the same host resource budget.
4. Content-address rendered units by exact inputs/runtime. Separate intrinsic media proof (decode, codec, alpha content) from contextual proof (placement/readability over actual footage, captions, transforms and semantic use). Identical alpha MOV bytes can reuse the first and still require the second at a new timeline location. A cache hit may reuse a proof only when media digest, complete dependency identity, validator version and proof policy match. Snapshot/read the exact bytes that render; metadata/mtime alone is inadequate. Re-prove unknown, corrupt or changed inputs.
5. Render only changed units for iteration. On initial build, reuse approved scene assets to assemble a complete review master. After repairs, reassemble affected closure and create one complete final master. Do not re-encode the full ten-minute picture for every local preview.
6. Run one reusable full-output measurement pass where filter semantics allow: timestamps, decode health, luma/color risks, black/freeze/flash candidates, audio levels/silence/peaks. Combine compatible analyses; cache results by final hash and checker version. Batch extraction of selected frames and seam clips from this index.
7. Technical checks cover the entire output. Model packets cover every required information claim and representative visual state, plus all risky/new/changed windows. Deduplicate identical timestamps/pixels across overlapping checks. Maintain an explicit coverage manifest instead of saying a model viewed every frame.
8. Include temporal clips at cuts, animation entrances/exits, source changes and suspicious audio windows. For longform, review the complete cut transcript/chapter structure and section-level audiovisual context. Static stills cannot establish motion, AV sync or sound quality. Admit the reviewer workload too: deduplicated clip seconds, images, claims and risk windows per responsibility. Coalesce nearby windows; a chapter clip may satisfy many seam/event obligations. Every flagged risk needs a disposition. If required evidence exceeds the calibrated reviewer budget, offer a longer estimate/class before work rather than drop coverage. Final-composite collision checks must include moving presenters during graphic holds, not only alpha assets and settled snapshots.

Fix placement-exemption coverage before using these receipts to justify narrower review. `placement_verify.py` currently skips a whole graphic on any b-roll/title-card overlap. A ten-second graphic with one second of covered footage still needs verification over the other nine seconds; test partial, full, disjoint and boundary-only overlaps explicitly.

Upstream confirms seek-based frame rendering and supports multiple CLI render/quality paths; local implementations and pins must be tested before using newer flags. See [HyperFrames rendering](https://hyperframes.heygen.com/guides/rendering) and [deterministic rendering](https://hyperframes.heygen.com/concepts/determinism). FFmpeg offers the measurement/filter primitives needed for combined analyses, but equality of our existing checks must be demonstrated: [official filter reference](https://ffmpeg.org/ffmpeg-filters.html).

## 7. Audio and color should be real finishing lanes

**Audio.** Keep Sniper's channel selection, local cleanup, ducking and measured master. Unify the stale music-mix normalizer with `audio/master.py`; test quiet/high-crest and high-LRA sources. Carry dialogue/music/SFX as floating-point PCM with headroom until the final master/quantization so intermediate AAC and repeated normalization do not accumulate. Current `dialogue_program_media.py:100` mixes float inputs but converts to s32 before the later master; qualification must catch saturation at that boundary. Reuse analysis and music-only remux paths where the actual graph permits.

Analyze speech-active windows across the program using real stems: dialogue level consistency, bed/SFX relative to speech, clipping before limiting, unexpected silence, seam clicks, hum and channel anomalies. Intentional pauses and music-only sections come from the plan. Keep restrained cleanup by default; strong separation is selected only for evidence-backed noisy material and must pass an original/processed audition.

Create a short audition reel from the hook, source transitions, quietest/loudest speech, worst masking/cleanup risks and ending. A validated audio-capable reviewer or the operator must actually hear risky audio; a visual model cannot certify it. Qualification includes blind headphone/speaker listening of the whole outputs. If per-job listening is required but unavailable, the job explicitly needs audio review and does not masquerade as fully approved; this limitation must be resolved before claiming unattended quality for that input class.

Retain project-level loudness/peak policy as a measured target, not a universal substitute for comfort. Bind final audio proof to exact mixed PCM and encode. Any changed pre-master samples can alter global loudness normalization, limiter behavior or ducking, so invalidate the complete mastered-audio proof and rerun required full-program audio checks, even for a local source/SFX edit. Unchanged source stems and unaffected picture can still be reused. Add typed SFX gain/remove/timing operations and their graph dependencies; `surgical-edit.ts` does not currently grant a dedicated SFX lane. Moving a graphic and lowering its sound must resolve both changes and their affected proof.

**Color.** Introduce a typed source/shot-group color track: input color transform → neutral correction → approved look/intensity → delivery transform. Reuse existing mezzanine normalization for supported technical cases. Persist source primaries/transfer/range, explicit camera Log profile where needed, chosen transform and correction parameters. Never guess an untagged Log source's transform from its flat appearance.

The ZIP contains a useful concrete starting point that the initial comparison underemphasized: `.claude/skills/media-use/scripts/lib/grade-analyzer.mjs:214–256`, exposed through `resolve.mjs --type grade --for` and `--analyze`, probes color metadata and samples FFmpeg signal statistics to suggest bounded exposure/contrast/whites/blacks/temperature/tint changes and flag HDR/incomplete color metadata. During this follow-up its existing `grade-analyzer.test.mjs` suite passed 10/10 tests with Node v23.10.0 and FFmpeg 8.0, without installation/network (763.33ms Node-reported total). These are small synthetic-frame and pure-statistics tests, not real-footage or rendered grading qualification. Its minimum 0.1fps sampling with a five-frame cap covers only approximately the first 50 seconds of a long input: replace this with full-timeline, source/lighting-group sampling before adoption. Global chroma estimates alone cannot distinguish a color cast from intentional colored lighting; neutral/skin/reference evidence and qualified rules must govern whether a suggestion is applied. Add explicit color-range metadata. Preserve warnings: normal `resolve.mjs:561–574` merges only the proposed adjustment fields, loses source/warnings, and overwrites existing same-name adjustments. Adopt analysis → reviewed proposal, not this unconditional merge into approved grades. This analyzer is distinct from the ZIP's default house-LUT workflow, which skips source correction.

Persist transform history and input/working/output color spaces for originals, proxies and mezzanines. Apply the input transform exactly once. Current qualified HDR normalization can produce 8-bit BT.709; it is not interchangeable with the original HDR/Log source for later correction. Preserve source-quality material or declare the limitation of a qualified intermediate. Test the real encoded/decode preview and browser playback against export, with explicit range/primaries/transfer/matrix tags; matching formulas on a PNG and MP4 alone does not prove appearance parity. Include already-transformed sources, HDR highlights, saturated brand text, gradients and alpha edges.

Group by camera/lighting conditions, not by every jump cut. Measure and preview representative highlights, shadows, neutral objects and skin where present. Show A/B using the same transform math as final encode. Apply one coherent approved look, with per-group correction; check scene-to-scene jumps and final color tags. Clipping/saturation detectors flag risk, while intentional dark scenes and saturated brand colors need content-aware decisions. Apply source correction and the creative look below graphics/captions so footage grading does not recolor brand cards or text. Declare a separate input/grade policy for each b-roll/screen/graphics asset; bring them into the same working color space before compositing, then perform the delivery transform consistently. Validate linear/nonlinear alpha and edge handling. Combine compatible operations into the final picture path without separate complete encodes for each knob.

Add a Color panel with source-profile selection when ambiguous, neutral correction, look/intensity and comparison; add typed color commands to the dispatcher and invalidation graph. Current `surgical-edit.ts` has no color lane. Preview-to-final color parity and source-specific transforms are release tests, not assumptions.

## 8. A falsifiable 120-minute allocation

This is an engineering budget, not measured throughput. It starts when the first post-cut creative brief is accepted, or at reviewed-cut availability when autopilot already has the brief. Proposal work is inside the clock in both modes; human approval is optional by policy. Genuine user wait is shown separately without hiding concurrent system work. An up-front one-request raw-to-master run retains the separate cut/preparation time and the provisional 155-minute overall system target; it is not a demonstrated 120-minute raw-to-master promise.

| Critical-path stage | Budget | Definition of done |
|---|---:|---|
| Storyboard, animated sample, sound/color proposal | 10m | Actual copy/source preview; reusable evidence; user or authorized system confirms treatment |
| Compile treatment plan + deterministic preflight + independent plan review | 15m | All clauses resolved, complexity admitted, same plan passes checks/reviews |
| Parallel graphics/captions/audio/color preparation | 25m | All required assets and finishing decisions ready; budget is the slowest branch plus contention |
| Complete picture/audio assembly | 15m | Full first candidate at delivery dimensions/rate, not a partial preview |
| Full technical scan + targeted audiovisual/craft review | 15m | Exact candidate has current evidence and covered responsibilities |
| Shared repair pool across proposal, planning, assets and post-render QC | 30m | Bounded repairs pass; stage transitions/resume never reset the pool |
| Promotion and delivery artifacts | 5m | MP4, captions/chapters as requested, receipts, UI playback available |
| Scheduling/variance reserve | 5m | Covers queue and startup variability |
| **Total** | **120m** | All failed and timed-out attempts still reported |

A clean run's allocation is 85 minutes before the 30-minute repair and five-minute variance reserve. The 15-minute review budget must include actual audiovisual review capacity; it cannot assume hundreds of images are free. If measurements disprove a budget, alter the implementation or honestly narrow the admitted workload; do not move system work off the clock.

Provisional short targets: 30–90s clean/light first master in 10–20 minutes; produced short in 20–35 minutes from the first accepted post-cut brief, with separate cold and dense/custom classes. These are additional targets requiring their own evidence, not an extrapolation from ten-minute throughput.

Revision targets to qualify: ordinary text/card preview within two minutes; audio-only audition within two minutes; local repair plus approved complete master within 10–15 minutes on the ten-minute class. Global grade, cut ripple and new custom motion get separate estimates. A fast local preview does not imply a fast fully re-approved final.

## 10. Evaluation, adversarial tests and decision rules

Use existing [performance testing](command-driven-editing/08_PERFORMANCE_AND_TESTING.md) and [P7/P8 audit](command-driven-editing/19_P7_P8_QUALIFICATION_AUDIT.md) as foundations. Add a practical corpus of creator footage rather than only synthetic mechanism fixtures.

- Pilot at least six long and six short projects across camera/screen, clean/noisy audio, supported color classes, light/produced density and caption policy; run cold and warm with the same accepted request. Include failures and fixes.
- Hold out at least three additional long and three short projects until implementation/tuning freezes. Freeze class limits before confirmation. If a confirmation failure causes any code/policy tuning, retain it and select newly untouched cases for the next confirmation; a repaired former holdout is now a regression fixture. These small cohorts can qualify named examples and expose failure modes; they cannot substantiate a p95 or 95%-reliability marketing claim.
- Record machine/chip, available RAM, disk/storage, thermal/power mode, background load, source dimensions/rate/codec, output duration, cuts, unique/total graphics, animated seconds, captions, source/lighting groups and asset state.
- Compare full outputs blindly for story/word integrity, pacing, useful graphics, readability, audio comfort/intelligibility, music balance, color consistency and final artifacts. Reviewers hear audio and watch motion. An improved elapsed time with worse output fails.
- Use seeded defects: wrong number/name, cropped words, low contrast, one-frame alpha leak, transition glitch, cut word, lost syllable, AV drift, hidden music masking, channel loss, denoise artifacts, wrong Log/HDR transform, color jump, stale assets and an omitted requested clause.
- Test unchanged source/proof reuse; then alter media bytes, text, overlapping captions, shared tokens, runtime, checker and cut timing. Each affected proof must invalidate, unrelated ones must remain reusable only when that is demonstrated.
- Test resume after interruption mid-render/mid-review and request-budget persistence; duplicate requests; output promotion after stale parent; bounded queue saturation. No new work should overwrite an approved parent.
- Track completion time and failure rate separately. A failed deadline is not a quick successful run. Report preparation + generation + wait + later edit clocks and the overall total.

Candidate release criterion for the named automatic first-master class: all held-out outputs pass technical/authority checks and required audiovisual/quality review, all required intent is represented, and every accepted held-out run completes within 120 minutes on the declared host. Assisted cases are reported separately and never relabeled automatic successes. If any fails, fix/retest prospectively and retain the failed attempt in the report. Broader percentile/reliability claims require a separately sized prospective cohort. Record the fraction of real creator requests admitted, rejected or sent to full/fallback workflows and their actual time; a narrow fast subset alone does not prove everyday editing is faster.

## 13. Confidence, quality and unresolved edge cases

**What is established:** the cited duplicated work and missing UI/quality capabilities exist in the inspected code; the ZIP contributes more than templates, including deterministic QA, motion/SFX coordination and a tested color-analysis starting point. The application has not incorporated these proposed transfers during this review. The new grade unit tests do not establish perceptual quality, and existing trim benchmarks do not establish produced-video throughput.

**What is plausible but unproved:** eliminating redundant decode, planning and whole-job repair should reduce elapsed time without requiring weaker content. Source-aware correction, speech-first mixing, better visual eligibility and earlier technical checks could improve consistency. No complete matched produced-video experiment has yet proved either unchanged or increased overall quality within two hours.

Separate implementation risk classes. Batching equivalent scans, preserving validated bytes and reusing exact dependency-bound artifacts aim to change execution cost, not editorial choices; still test extraction equivalence, cache validity and resource contention. Smaller model contexts, fewer review images, different reviewers and recipe/density constraints can change defect recall or editorial output and require quality comparisons. Restricting a performance qualification class is honest measurement, not permission to make every video fit 30 graphics or remove requested creativity. Allow separately estimated bespoke work when its value justifies the cost.

| Missing or easily underestimated case | Required response / proof |
|---|---|
| A clean cut changes meaning: a missing “not,” removed caveat, wrong repeated take, or narration no longer aligned with the demonstrated action | Compare retained story/claims with source meaning and action/referents, not just transcript token/number membership; inspect cut handles and whole-program flow |
| Every frame passes but the edit is boring, distracting or redundant | Evaluate comprehension, narrative progression, visual purpose and breathing room across the complete video; blind full-output viewing/listening remains necessary in qualification |
| Lighting changes late in a long recording; mixed cameras or an already-normalized proxy | Sample the whole timeline by source/lighting group; preserve transform history, avoid double conversion and uncertain global casts; verify encoded/browser appearance |
| Dialogue, music or SFX changes create pumping, lost consonants, awkward pauses or late masking | Listen to original/processed risk passages and full qualification outputs; preserve prosody, recompute global master proof after any pre-master sample change; metrics alone cannot certify comfort |
| Presenter moves underneath a graphic, captions collide mid-animation, or partial b-roll overlap wrongly exempts the whole graphic | Fix the concrete `placement_verify.py:156,194` whole-clip skip; check uncovered intervals and actual motion, not only an opening still or catalog thumbnail; treat dense captions and moving subjects as workload/risk features |
| Incorrect ASR, accents, code-switching, names/numbers, or non-English footage | Current `cut-review-prompt.ts:54` is transcript-only and timing checks validate shape, not spoken truth. Check high-consequence/uncertain words against source audio; declare actual language support, expose corrections and preserve source word IDs; English-default/synthetic coverage does not qualify every input |
| “Keep everything” conflicts with “make it ten minutes,” a style reference conflicts with legibility, or a required asset is missing | Durable per-clause disposition; ask only the necessary decision or use an explicitly preauthorized alternative, never silently drop the clause |
| A local change affects global story, normalization, timing or a human-owned edit; retries/resume run against stale parents | Dependency-based invalidation plus global checks where required; preserve approved parent and ownership; continue the original budget across recovery |
| Cold assets, dense graphics/captions, low disk, multiple jobs, unsupported codec or thermal contention | Admit from actual compiled cost and source/host limits, measure all queue/retry time, surface changed estimates; do not count missing requested work as a successful fast result |

The next decisive proof is a complete ten-minute creator project through the intended GUI route, with the same source/brief/style rendered by the baseline and optimized workflow, followed by a scoped revision. Track full clocks, every failure and active user time; compare story integrity, visual usefulness/readability, motion, sound and color by blinded whole-output review. This is the first falsification test, not a substitute for the larger held-out cohort in §10. Report technical quality, editorial quality and elapsed time separately: technical improvements alone do not establish that the video is better.
